# Security Checklist

Health, nutrition and body-measurement data is sensitive personal data. The
posture is deny-by-default, and correctness here is not negotiable.

## Status legend

- **Done** — implemented and verifiable in this repo
- **Required before launch** — designed for, not yet built
- **Ongoing** — needs periodic re-checking

---

## Authentication and session handling

| Item | Status | Where |
| --- | --- | --- |
| Supabase Auth as the only identity source | Done | `src/lib/supabase/*` |
| Session validated with `getUser()`, never `getSession()` | Done | `src/middleware.ts` |
| Unauthenticated requests redirected away from app routes | Done | `src/middleware.ts` |
| API routes re-check auth server-side, not just in middleware | Done | `src/app/api/food/analyze/route.ts` |
| Email verification enforced | Required before launch | Supabase dashboard |
| Rate limiting on auth endpoints | Required before launch | Supabase / Vercel Firewall |

`getSession()` reads the cookie without verifying it and can therefore be
spoofed. `getUser()` validates against the auth server. Anywhere an
authorisation decision is made, it must be `getUser()`.

## Row Level Security

| Item | Status |
| --- | --- |
| RLS enabled on **every** user-owned table | Done — `0008_rls.sql` |
| Separate policies per command (`select` / `insert` / `update` / `delete`) | Done |
| `INSERT` policies use `with check`, `UPDATE` uses both `using` and `with check` | Done |
| Policies scoped `to authenticated` — `anon` reaches no user data | Done |
| `auth.uid()` wrapped in a subselect for per-statement evaluation | Done |
| Every column referenced by a policy is indexed | Done |
| Child tables inherit ownership through their parent | Done — `grocery_items`, `recipe_ingredients` |
| Users cannot publish custom foods or recipes to other users | Done — `is_public = false` forced in `with check` |
| **Admins are not granted blanket read access to user health data** | Done — deliberate omission |
| Automated cross-user access tests in CI | Required before launch |

Admin policies exist for content tables (foods, recipes, exercises, lessons) but
deliberately **not** for user data. Support workflows should go through audited,
purpose-specific server functions, so "any admin can read anyone's health
record" is never true by default.

## Secrets

| Item | Status |
| --- | --- |
| Service-role key never in a `NEXT_PUBLIC_` variable | Done |
| Service-role key importable only server-side | Done — `import 'server-only'` in `admin.ts` |
| AI provider keys server-side only | Done — all AI calls in route handlers |
| `.env.local` gitignored; `.env.example` carries no real values | Done |
| Secret scanning in CI | Required before launch |
| Key rotation procedure documented | Required before launch |

The `server-only` import in `src/lib/supabase/admin.ts` turns "someone imported
the admin client into a React component" from a silent production leak into a
build failure.

## Tests to write before launch

```
tests/rls/
  own-rows.test.ts          user reads and writes their own rows
  cross-user.test.ts        user B cannot read user A's rows — every table
  anonymous.test.ts         anon reaches no user data
  storage.test.ts           user B cannot read user A's meal photos
  admin-scope.test.ts       admin can edit foods, cannot read health data
  custom-food.test.ts       a user cannot set is_public or is_verified
```

These require a running Supabase instance and so are not in the default `npm
test` run, which covers the pure engines only.
